`pi-keys` 把普通的环境变量凭据变成一个可供 [Pi](https://github.com/earendil-works/pi) 使用的密钥池。它保留当前可用的密钥，只在助手响应失败后切换。Pi 既有的重试、退避、取消和会话恢复行为完全不变。

## 快速开始

```bash
export OPENAI_API_KEY=key-a
export OPENAI_API_KEYS=key-a,key-b,key-c
pi -e ./index.js
```

也可以把扩展安装到 Pi：

```bash
pi install /absolute/path/to/pi-keys
```

配置到此为止：没有运行时依赖，没有构建步骤，也不需要单独的轮换配置文件。

## 现在能做什么

- **每个提供商一个密钥池。** 每个 `*_API_KEYS` 变量为对应的 `*_API_KEY` 定义逗号分隔的密钥池。`OPENAI_API_KEY` 对应 `OPENAI_API_KEYS`，`ACME_API_KEY` 对应 `ACME_API_KEYS`，依此类推。
- **自定义提供商无需改动。** 只要现有的 Pi 提供商配置引用了单数变量，密钥池就会生效：

  ```json
  { "apiKey": "$ACME_API_KEY" }
  ```

- **保留可用的密钥。** 只有助手消息以 `error` 结束时才轮换。成功响应、已中止的请求和工具错误都不会触发轮换。
- **同一提供商、同一端点。** 扩展只更换凭据，不改变请求路由，也不会选择其他提供商或模型。
- **没有隐藏状态。** 不写入凭据文件，不记录密钥；轮换游标就是解析出的密钥本身。
- **零运行时依赖。** 一个很小的扩展文件，配有单元测试和可选的端到端冒烟测试。

### 输入约定

扩展信任调用方满足以下条件，不做校验或修复：

- 每个密钥池中的密钥都非空且互不相同（首尾空白会被去掉）。
- 同一个密钥不会出现在不同的密钥池中。
- 单数变量存在，且初始值等于密钥池的第一个密钥。
- 模型确实通过该环境变量完成认证。不要用 `--api-key`、已保存的 `/login` 凭据或配置中的字面密钥覆盖它。

### 重试设置

沿用 Pi 现有的重试设置，例如：

```json
{
  "retry": {
    "enabled": true,
    "maxRetries": 1000000,
    "baseDelayMs": 2000,
    "maxAgentDelayMs": 60000,
    "provider": { "maxRetries": 0 }
  }
}
```

这是一个较大的有限预算，不保证无限重试。助手成功响应后，Pi 会重置智能体重试计数。Pi 在每次单独尝试之间等待，而不只在密钥池耗尽后等待。关闭提供商内部重试，可以让失败先到达 Pi，从而在下一次尝试前完成轮换。

## 边界与限制

- **轮换不会让错误变成可重试错误。** Pi 的分类器能识别常见的限流、服务器和传输错误，但并非所有 4xx/5xx 都算。在 Pi 1.1.0 中，包括 `insufficient_quota`、`quota exceeded` 和 `billing` 在内的配额/计费措辞会明确阻止自动重试，即使响应是 429。加大重试预算不会改变分类结果。扩展仍会在这类失败后轮换密钥，但 Pi 可能结束本次运行；它不会改写错误来绕过该策略。
- **上下文溢出仍由 Pi 负责。** 扩展会在任何助手 `error` 时轮换，包括 Pi 随后用压缩处理的错误。
- **并发请求不会互相协调。** 共享同一密钥池的请求在途时不会被跟踪：钩子在失败后解析认证信息，而不是记录每个请求实际使用的凭据。受支持的路径是普通的顺序智能体请求。
- **部分提供商扩展不在支持范围内。** 如果某个提供商扩展只捕获一次密钥、绕过 Pi 认证，或只把密钥放在自定义请求头中，无法保证可用。
- **不处理外层进程。** 扩展不会延长工作流超时、不会选择其他提供商或模型，也不会恢复已终止的进程。

## 架构

```text
index.js — 单个扩展，无依赖
│
├─ 初始化
│    扫描 process.env 中的 *_API_KEYS
│    建立 密钥 → 密钥池 的查找表
│
└─ message_end（助手消息，stopReason === "error"）
     ├─ 在 Pi 的模型注册表中找到实际的提供商/模型
     ├─ 用 getApiKeyAndHeaders() 解析其凭据
     ├─ 若该密钥属于某个密钥池，则切换
     │    process.env[<PROVIDER>_API_KEY] = 下一个密钥
     └─ 直接返回，不替换消息，也不安排额外工作
```

接下来发生什么由 Pi 决定。解析出的密钥同时充当轮换游标，因此不存在会过期的独立索引或提供商映射。初始化不会修改单数变量。环境变更只作用于 Pi 进程及其随后启动的子进程，不影响父 shell。

在已验证的 Pi 版本中，内置的环境认证和自定义 `models.json` 环境引用都会在请求时解析密钥，因此无需刷新注册表或清理缓存。

## 如何开发

```bash
npm test                    # 单元测试：轮换、游标、非错误消息
PI_KEYS_SMOKE=1 npm test    # 可选：用真实 Pi 重试运行的端到端测试
```

冒烟测试要求 `PATH` 中存在 `pi`。它会创建隔离的临时设置和一个本地假的 OpenAI 兼容服务器，只使用测试密钥。测试验证真实 Pi 在交替出现 429/500 失败后的重试，包括完整走完一轮密钥池，覆盖内置提供商和自定义 `models.json` 提供商两种情况。不会调用任何外部 API。测试有执行时限，结束后会删除临时配置。

已在 Pi 1.1.0 上验证。不对更广泛的提供商覆盖或配额错误最终必然恢复作承诺。

## 路线图

**已实现**

- 为任意 `*_API_KEY` / `*_API_KEYS` 组合发现环境变量密钥池，并支持循环轮换。
- 支持内置提供商，以及引用环境变量的自定义 `models.json` 提供商。
- 单元测试覆盖轮换、游标行为和非错误消息。
- 可选的端到端冒烟测试，覆盖 429/500 后的真实 Pi 重试和完整密钥池循环。
- 不写文件、不记录密钥，也没有需要同步的独立状态。

**计划中（目前不作承诺）**

- 协调共享同一密钥池的并发在途请求。
- 扩展内置提供商和自定义 `models.json` 之外的提供商覆盖范围。
- 当 Pi 的分类器拒绝重试配额或计费失败时，给出更清晰的行为说明；这取决于 Pi 策略，扩展不会强行绕过。

未来愿景刻意保持很小：密钥池应当像一份持久凭据那样工作，不需要守护进程、状态文件或额外配置。随着 Pi 扩展 API 的发展，`pi-keys` 应继续做一个紧凑的适配层，把所有调度、重试和恢复决策交给 Pi。
